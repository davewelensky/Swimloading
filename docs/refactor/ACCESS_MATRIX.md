## Design notes

- **Why `/growth-hub` isn't fully migrated to `user_roles`:** it already has genuine, working, RLS-enforced access control (`growth_sponsors`'s `founders_all` policy checks `auth.jwt() ->> 'email' IN (SELECT email FROM growth_founders)`, confirmed by reading the live policy). Migrating it now would be scope creep with no security benefit — the instruction was "do not reuse `growth_founders` as the *platform-wide* model," not "rebuild something that already works." The one gap is that `platform_admin` (a new concept) currently has no path in — adding that is a small, additive change once `user_roles` exists, not a rebuild.
- **`content-calendar.html` is the one page where "unauthorised behaviour" is currently "full exposure"** — it has zero auth today (confirmed in the prior security pass). Every other page at least has *some* gate, even if weak. This makes it the highest-priority page to actually migrate once Step 3 is approved and built.
- **Direct navigation:** none of the six pages are linked from any public-facing page (confirmed for `/dave`, `/Sponsors/`, `/content-calendar`, `/caption-agent` in the prior session's grep sweep; `/admin`, `/PHtest`, `/growth-hub` share the same `robots.txt`/`noindex` treatment but weren't individually re-confirmed this pass — low risk either way since they're all `noindex`+`Disallow`already).
- **Scope for `/PHtest`:** currently hardcoded to exactly 2 user IDs (Dave, Carina) — a real, narrow test cohort, not a general audience. The role matrix intentionally keeps that narrow (`partner_viewer` scoped, optional) rather than opening it to all `partner_manager`s by default.
